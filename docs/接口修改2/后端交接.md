# 后端交接（本次接口契约改动）

**总量**：operation 由提交前的 **68** 变为 **64**，净减 4。构成：删除 35 个旧 operation、新增 31 个（多数属改名/归组/拆分后的同功能接口，见第 12、15 节及题目、通知章节说明）。旧 URL 与 `operationId` 均不保留；两端尚未上线，全部按可重写处理。`check_contract.py` 通过。

> **阅读说明**：本文档为累积式变更日志，按时间顺序记录。少数早期小节描述的是中间态，后续小节（以及最终的 `api.md` / `apifox-import.json`）已对其细化或反转；**如遇冲突，以靠后的小节和当前契约文件为准**。最终净状态集中在 §38–§45。

## 1. 题目管理：新增写接口 + 四接口统一挂到 `/admin/photos`

- **新增 2 个 operation**（表单 `AdminPhotoUpsertForm`，`multipart/form-data`）：
  - `POST /admin/photos`（新增题目，`adminCreatePhoto`）：所属活动用**必填表单字段 `activity_id`** 指定（活动不存在返回 `400`）；管理员可给**未开始或进行中**活动（`now < end_time`）新增题目，已结束活动不可新增（返回 `400`、`code=5`），新增后直接 `approved`；作者规则本轮由「记为当前管理员」改为「**固定记为官方账号**」（见下）。
  - `PUT /admin/photos/{id}`（更新题目，`adminUpdatePhoto`）：编辑题目内容，不改变审核状态；编辑 `rejected` 题目也不会重新进入审核或恢复公开；至少提交一个字段，改坐标时 `longitude/latitude/coord_type` 必须成组提交；题目不存在返回 `404`。
- **`GET /admin/photos/pending` 改名为 `GET /admin/photos`（题目列表），并升级为管理端唯一题目列表**：旧名会把它误导成"只查待审核"，实际返回全部活动、全部审核状态（`pending/approved/rejected`）的未删除题目，故去掉 `/pending` 后缀。本轮为其新增两个可选参数：`activity_ids`（重复参数 `activity_ids=1&activity_ids=2`，多个活动 ID 之间 OR）和 `keyword`（题目 ID、标题、描述、作者 ID 或昵称，≤50），与 `status` 按 AND 组合。列表项 schema 改为 `AdminPhotoListItem`，新增所属活动 `activity`（`ActivityBrief`，仅 `id`、`title`）；计数字段为 `attempts_count`（作答数）、`solved_count`（作答成功数，新增）、`likes_count`（点赞数），**不返回 `solved` 布尔**——是否被破解由 `solved_count > 0` 推导，避免冗余字段；同时新增 `solved` 布尔筛选参数（`true` 即 `solved_count > 0`）。
- **归组与命名**：题目列表、新增题目（`POST /admin/photos`）、更新题目（`PUT /admin/photos/{id}`）、审核题目（`PUT /admin/photos/{id}/review`，展示名由"审核图片"改为"审核题目"）四个接口统一挂在 `/admin/photos` 资源下，不再使用 `/admin/activity/{activity_id}/photos` 前缀；api.md 中对应小节也已并入"题目管理与审核"一章。

行为含义：管理端只有一个跨活动、可多活动筛选的题目列表查询；不提供按单个活动读取题目的接口。旧 `/admin/photos/pending` 不再作为契约路径。题目与活动的从属关系在创建时由表单字段声明，URL 不再承载活动上下文。

行为含义（作者规则）：官方账号是部署侧预置的一条真实用户记录（昵称如“图寻官方”），管理端新增题目时 `photos.user_id` 固定写入该账号；客户端和管理端各接口返回的 `author` 就是该账号的 `UserBrief`，契约不新增渠道字段。运营以个人身份投稿仍走 `POST /photos` 普通流程、正常审核、入库本人 ID。实际操作的管理员是谁属于后端内部审计需求，如需记录由后端自行加内部字段，不进契约。

- 题目**暂不提供删除接口**（`DELETE .../photos/{photo_id}`）：审核为一次性、编辑接口已可修正内容问题，故先只支持新增/编辑。代价是已通过题目暂时只能改内容、无法整体下架或隐藏；未来确有下架需求时再补 `DELETE`（或把审核改为可重复以支持 approved→rejected 撤下）。

## 2. 通知体系重做：通知与互动消息拆分为两组接口（原"公告"统一改叫"通知"）

原有混合的通知模型（`Notification` + `category`/`type` 组合、全局通知、未读数、标记已读等）整体重做，与提交前相比最终形态如下。

**通知（`/announcements`，管理员发布；中文名定为"通知"，不再叫"公告"）**

- `GET /announcements`（通知列表，登录可用，管理端复用）：分页返回 `id`、`title`、`content_preview`（后端从完整正文生成：去 `[image]` 占位、合并空白、按 Unicode 码点截前 50 字）、`is_read`、`created_at`，响应必返 `unread_count`（当前用户未读通知数，角标用）；`keyword`（≤50）匹配原始完整正文。拉取列表不改变已读状态。
- `GET /announcements/{id}`（通知详情）：返回完整 `content`（保留 `[image]` 占位）、可选配图 `image_url`、可选活动关联 `related_type`/`related_id`（`activity`，同返同省）。**读取成功即对当前用户标记已读**（读即已读，幂等），`is_read` 为读取前状态；不设标记已读接口。
- 管理端写接口：`POST /admin/announcements`（发布）、`PUT /admin/announcements/{id}`（更新，`remove_image`/`remove_relation` 开关不得与对应新值同传）、`DELETE /admin/announcements/{id}`。表单：`title`（≤20）、`content`（≤5000）、可选 `image_file`（jpg/png ≤20MB）、可选 `related_type`+`related_id`（仅 `activity`，引用不存在返回 `400`）。发布走 `multipart/form-data`。
- 通知无过期时间、无弹窗机制；首屏弹窗改为独立的内容位资源（见第 16 节），可反向关联一条通知。

**互动消息（`GET /notifications`）**

- 仅剩点赞、评论两类（`type` 枚举 `like`/`comment`；原 `review` 审核通知删除——审核状态在"我的投稿列表""我的作答列表"自行查看，后端移除审核时写通知的逻辑）。
- 列表项：`id`、`type`、`user`（发送者 `UserBrief` 摘要）、`related_type`/`related_id`（`photo`/`solve`/`comment`）、`content`（后端按事件生成的单行文本）、`is_read`、`created_at`，全必返；响应必返 `unread_count`。`type` 为可重复参数（`type=like&type=comment`，OR）。
- 拉取列表**不改变已读状态**；未读通过 `PUT /notifications/{id}/read`（标记单条）与 `PUT /notifications/read-all`（一键全部）更新，`unread_count` 与各条 `is_read` 为读取前状态。不设互动消息详情。

**与提交前相比删除/替代的接口与字段**

- 删除 `GET /notifications/{id}`（通知详情）、`GET /notifications/unread-count`（未读数）、`GET /notifications/global-announcement`（全局通知）；互动消息改为"拉取不自动已读"后，改由 `PUT /notifications/{id}/read` 与 `PUT /notifications/read-all` 两个标记接口维护已读（见 §35）；`POST /admin/notifications` 由 `/admin/announcements` 系列替代（请求由 JSON 改为 multipart，新增图片能力）。
- 字段删除：`category`（可由类型直接判断，冗余）、`expires_at`（通知无过期时间）；通知正文上限定为 **5000**（原无上限，§6 长度表同步）。
- schema：`Notification`/`NotificationListItem`/`NotificationPage` 删除，新增 `Announcement`/`AnnouncementListItem`/`AnnouncementPage`/`InteractionMessage`/`InteractionMessagePage` 和 `CreateAnnouncementRequest`/`UpdateAnnouncementRequest`。

行为含义：通知是管理员的信息发布位（可配图、可跳活动，读详情记已读）；互动消息是消息中心（拉取不自动清未读、由标记接口清，点击按关联对象跳转）。两者角标分别取自各自列表响应的 `unread_count`。整节均属破坏性重做，两端未上线按可重写对待。

## 3. 管理端搜索与筛选（本轮补充/明确的字段）

- 管理端题目列表：新增 `activity_ids`、`solved`、`keyword`（见 §1）。
- 作答审核、评论审核列表：路径由 `/admin/attempts/pending`、`/admin/comments/pending` 改名为 `/admin/attempts`、`/admin/comments`（与统一题目池一致，去掉误导性的 `/pending` 旧名），默认改为返回全部状态、`pending` 降为 `status` 筛选值；本轮另新增 `keyword`。作答列表返回猜测坐标与题目答案坐标（本轮为离散 `coord_type`，后由 §36/§37 统一聚合为 `Location`：`guess_location`、`photo.location`）；评论列表每条记录返回当前 `status`，不能用筛选条件推断混合结果中的单条状态。
- 管理端活动列表 `GET /admin/activity`：`keyword` 支持按活动 ID、标题或描述搜索，`status=not_started|active|ended`（后端按服务器当前时间计算）。
- 管理端奖品列表 `GET /admin/goods`：`keyword` 支持按奖品 ID、名称或描述搜索，`status=in_store|out_store` 看下架奖品。
- 管理端通知列表 `GET /admin/announcements`：`keyword` 支持按通知 ID、标题或正文搜索。
- 兑换列表新增 `exchange_id`、`user_keyword`、`good_keyword`；反馈列表新增 `keyword`；`GET /admin/users` 的 `keyword` 对用户 ID / 学号 / 姓名 / 昵称做 OR 模糊匹配（**不设逐字段精确参数**，见第 17 节），另有 `status`、`level` 筛选。字符串搜索参数一律 ≤50，搜索与筛选同时提供按 AND 组合。各接口 `keyword` 支持的具体字段以《约定》"客户端搜索""管理端搜索字段"两条为准。
- **搜索口径定稿（客户端与管理端拆分接口）**：活动、奖品、通知三类**各拆为客户端 + 管理端两个列表接口**：客户端 `GET /activity`、`GET /goods`、`GET /announcements` 的 `keyword` 纯文字模糊匹配、不支持按 ID，且无任何按调用者等级变化的分支（`GET /goods` 连 `status` 参数也去掉，客户端只返回上架奖品）；管理端 `GET /admin/activity`、`GET /admin/goods`、`GET /admin/announcements`（均 Level ≥ 2）的 `keyword` 支持按 ID 搜索，`/admin/goods` 带 `status` 看下架、`/admin/activity` 带 `status` 时间态。管理端列表复用客户端的响应 schema（活动 `ActivityCardPage`、奖品 `GoodItemPage`、通知 `AnnouncementPage`），不重复定义结构；活动/奖品仍不设详情接口（列表项已全字段）。通知因列表只有 `content_preview`、需要详情取全文，且客户端详情有"读即已读"副作用，故**管理端另设 `GET /admin/announcements/{id}`**（Level ≥ 2、读取不标记已读）供编辑回填，与列表拆分对称。这样客户端接口零管理员分支、管理端权限统一为 Level ≥ 2，避免早前"按 Level 隐式改变 keyword 语义"会误伤管理员客户端搜索的问题。奖品列表项抽为公共 `GoodItem` / `GoodItemPage` 供两端共用。

## 4. 权限等级与账号状态模型（本轮细化）

- 术语：文档统一把“超级管理员”改为“**创世管理员**”，由部署侧管理、可存在多个；同时明确 Level 3 只能由部署侧治理，业务接口不再把未登录当作用户账号等级。
- **登录态、权限等级、账号状态三者相互独立**：未登录只是当前请求没有有效 Session，不写用户表、也不把 `level` 记为 0；账号 `level` 只允许 `1/2/3`，`status` 独立为 `active/banned`；封禁/解封不改 `level`，调级不改 `status`。

**用户治理仅限 Level 3**：用户列表（`GET /admin/users`）、封禁/解封（`PUT /admin/users/{id}/status`）、调整等级（`PUT /admin/users/{id}/level`）都只有创世管理员可调用，Level 2 调用返回 `403`；普通管理员只负责内容审核与运营，不接触用户账号。

| 操作者 | 可封禁 / 解封 | 可调整等级 |
|-------|---------------|------------|
| Level 1、Level 2 | 无 | 无 |
| Level 3 | Level 1、Level 2 | Level 1、Level 2 之间调整 |

- `PUT /admin/users/{id}/status` 仅 Level 3 可调用；任何人操作 Level 3 账号返回 `403`（`code=7`）；封禁后立即吊销目标全部 Session。
- `PUT /admin/users/{id}/level` 仅 Level 3 可调用，`target_level` 只允许 `1` 或 `2`；Level 3 之间不能互相治理，也不能治理自己。Level 3 的创建/修改/删除及状态、等级变更只能走部署侧受控流程，业务用户列表只读展示其摘要。

## 5. 文本字段长度统一定稿（字段级收紧）

请求侧文本字段长度本轮全部定稿，均按 Unicode 码点计数，超长返回 `400`；相关 operation 的 `responses` 已补齐 `400` 声明；`api.md`《约定》保留标题统一条目，其余在各接口参数表逐字段标注。原值 → 现值：

| 字段 | 原值 | 现值 |
|------|------|------|
| 所有 `title`（题目 / 活动 / 通知 / 反馈） | 无上限 / 255 / 128 / 100 | **20** |
| 昵称 `nickname`（`PUT /user/nickname`） | 20 | **10** |
| 题目描述 `description`（投稿、管理端题目表单） | 无上限 | **50** |
| 活动描述 `description`（创建 / 更新活动） | 无上限 | **100** |
| 奖品名称 `name`（`GoodUpsertForm`） | 50 | **20** |
| 奖品描述 `description`（`GoodUpsertForm`） | 500 | **50** |
| 通知正文 `content`（发布 / 更新通知） | 无上限 | **5000** |
| 驳回原因 `reject_reason`（图片 / 评论审核 `ReviewActionRequest`、作答审核） | 无上限 | **50** |
| 评论 `content` | 500 | **140** |
| 反馈内容 `content` | 500 | 500（不变） |
| 反馈联系方式 `phone` | 20 | 20（不变） |
| 列表搜索 `keyword`（全站） | 50 | 50（不变） |

属于收紧校验（破坏性改动），两端均未上线，按可重写对待，无需过渡方案。

附带修正：`POST /photos` 与 `POST /photos/{id}/attempts` 的 `coord_type` 此前只在描述里写了 `wgs84/gcj02/bd09` 而未声明 `enum`（管理端表单已有），本轮补上 enum，使 spec 与既有文字一致，合法取值不变。

行为含义：标题、奖品名是卡片单行位，20 字防溢出；题目/奖品描述是卡片两三行位，50 字；活动描述给 100 字容纳简短规则说明；评论 140 字（对齐微博单条长度）防刷屏保排版；管理员长文（通知正文、内容位富文本）统一 5000（富文本含标签），后端只记一条规则；标题、名称、描述、驳回原因等短字段是排版约束，维持各自数值——服务端对管理端请求仍做校验（管理员 Session 也可能被盗用），只是校验就一行 maxLength，不构成负担；驳回原因 50 与列表展示宽度匹配。除协议明确生成的 `content_preview` 外，响应侧存量业务字段 schema 按契约风格不标请求长度；后端存量数据无需迁移（无上线用户）。

## 6. 资料修改频率限制（新增 `429` / `code=9`）

- 修改昵称 `PUT /user/nickname`：昵称每自然月最多修改 **4 次**（按服务器时区，自然月初重置）。仅当请求携带 `nickname` 且与当前昵称不同时计 1 次，且成功修改才计数；提交相同昵称不计数、不报错。
- 修改头像 `PUT /user/avatar`：每自然月最多修改 **10 次**（同上计数口径，成功修改才计数）。
- 超限统一返回 `429`，新错误码 `code=9`（message 前缀「频率限制」），已登记进状态码表、错误码表和 OpenAPI `ErrorResponseBase.code` 枚举；两个 operation 的 `responses` 已声明 `429` 及示例。剩余次数不另设查询接口，而由 `GET /user/info` 响应新增两个必返字段暴露：`nickname_edits_remaining`（本月剩余昵称修改次数，0–4）、`avatar_edits_remaining`（本月剩余头像修改次数，0–10），均按服务器时区自然月初重置，供前端展示与禁用按钮。
- 实现只需按（用户，自然月）计数；无上线用户，无历史数据回溯问题。
- 附带修正：`PUT /user/avatar` 此前从未声明 `400`，本轮补上（文件类型或大小不符，`code=3`），属声明缺口修正，行为不变。

行为含义：限制昵称频繁更换以保持社区内身份可辨识，限制头像反复上传以控制存储与审核成本。数值(4/10)后续调整属于放宽或收紧校验，按契约流程改文档即可。

## 7. 删除作答文字字段 `answer_text`（字段删除）

- 从以下 3 处 schema 及对应示例中整体删除 `answer_text`：提交作答 `POST /photos/{id}/attempts` 请求、图片下作答列表项（现 `GET /photos/{id}/solves`）、`UserAttemptItem`（我在本图的作答与我的作答记录共用）。该字段因此不在 §6 的长度定稿表中。
- 作答的构成改为：猜测图片 `image_file` + 猜测坐标，判定与展示均不再有自由文本。

行为含义：管理端作答列表本就不返回 `answer_text`，审核判定只依据猜测图片与坐标，该字段对判定无贡献；但它会在客户端作答列表公开展示，且作答审核（`solved`/`unsolved`）并不是对文本的内容审核，等于一个未经审核的公开文本发布口。删除后表达类需求统一由评论承载（评论有独立审核流程）。属于删除字段的破坏性改动，两端未上线按可重写对待；后端可一并删除对应存储列，无历史数据迁移问题。

## 8. 活动结束后公开题目答案坐标（新增响应字段）

- 图片详情 `GET /photos/{id}`：新增**条件返回**字段 `longitude`、`latitude`、`coord_type`——仅当题目所属活动已结束（服务器时间 ≥ `end_time`）时返回，活动进行中或未开始时这三个字段不出现在响应中；坐标为投稿时提交的原始值与坐标系。字段不进 `required`，前端以字段是否存在判断答案是否已揭晓。
- 该 operation 的 `description` 原本已写明「活动结束后揭晓真实坐标」，但 schema 从未声明过这三个字段（文字与结构脱节），本轮补全使其可实现、可生成类型。
- 附带修正：我的投稿详情 `GET /photos/user/{id}` 原本返回 `longitude/latitude` 却缺 `coord_type`（没有坐标系的经纬度无法正确落图），本轮补上（必返）。用户作答记录 `UserAttemptItem` 同步补上必返 `coord_type`；管理端作答列表同时补上 `guess_coord_type` 与题目答案的 `coord_type`。（这些离散坐标字段后经 §36/§37 统一聚合为 `Location`；`UserAttemptCard` 已不返回作答坐标，见 §30/§42，以最终为准。）
- 公开题目卡片（`PhotoCard` / `UserPhotoCard`）不新增题目答案坐标，答案只在详情接口揭晓；用户作答记录保留已有的猜测坐标并补齐 `coord_type`，管理端审核列表返回管理所需的题目答案坐标及两套坐标系。均为新增响应字段，非破坏性改动。

行为含义：活动进行期间坐标是谜底，必须由接口层面不下发（不能依赖调用方隐藏）；结束后详情接口可返回答案位置。活动一旦结束并可能公开坐标，不允许再通过更新活动把 `end_time` 延长到当前时间之后重新开放；若需提前结束可将 `end_time` 调到当前时间之前，但之后同样不可撤回。管理端题目池和作答审核列表一直返回管理所需的坐标及坐标系。

## 9. `ActivityBrief` 精简（字段删除）

- `ActivityBrief` 由原来的 `id`、`title`、`description` 收紧为仅 `id`、`title`；共影响 5 个 schema 使用点（图片详情、我的投稿详情、图片/投稿卡片、用户作答项、管理端题目池），Markdown 示例中对应的 7 处嵌套 `activity` 也同步删除 `description`。
- 这是响应字段删除的破坏性改动；两端尚未上线，按可重写处理。完整活动列表和活动详情自身仍保留活动 `description`，只精简嵌套的活动摘要。

## 10. 创建活动封面必填（收紧校验）

- 创建活动 `POST /admin/activity`：`cover_file` 由可选改为**必填**（进 multipart schema 的 `required`），仍为 jpg/png ≤20MB。
- 更新活动 `PUT /admin/activity/{id}` 的 `cover_file` 保持可选，并明确语义：不传则保留原封面，传了则替换。因创建时已强制上传，活动在任何时点都必有封面。
- `ActivityCard.cover_url` 本就是必返字段，本轮改动使请求侧与响应侧自洽：后端不再需要处理"活动无封面"的分支。

行为含义：活动卡片以封面为主视觉，缺封面会破版；必填后前端无需准备占位图逻辑。属收紧校验的破坏性改动，两端未上线按可重写对待。

## 11. 管理端作答/反馈与互动通知补发送者摘要 `user`（新增响应字段）

- 以下位置新增 `UserBrief` 结构的 `user` 字段（`{ "id": 1, "nickname": "张三", "avatar_url": "https://media.example.com/avatars/avatar.jpg?signature=example" }`）：
  - 管理端作答列表 `GET /admin/attempts` 列表项：必返，作答者摘要；
  - 反馈列表 `GET /admin/feedback` 列表项：必返，反馈提交者摘要；
  - 反馈详情 `GET /admin/feedback/{id}`：必返（原 `user_id` 数字字段删除——`user.id` 已含该信息，不留冗余）；
  - 互动消息 `InteractionMessage`（`GET /notifications` 列表项）：必返，点赞/评论者摘要（通知体系重做后不再有 `sender_id`，见第 2 节）。
- 反馈详情原 `user_id` 字段随之删除：`user.id` 已含该信息，两端未上线无需为兼容保留冗余字段。

行为含义：这些界面此前只有发送者数字 ID，前端要展示"谁答的题 / 谁提的反馈 / 谁赞了你"必须逐个查用户，且普通接口并没有按 ID 查任意用户的入口；补上摘要后列表和详情可直接渲染昵称与头像。均为新增响应字段，非破坏性改动，提交后通知即可。

## 12. 接口精简（接口删除 + 合并 + 新增响应字段）

通知体系的删除与替代见第 2 节；其余与提交前相比删除的 operation 如下：

- **删除图片流展示与图片下载**：`GET /photos/{id}/image`、`GET /photos/{id}/download`。《约定》媒体 URL 条目已规定所有图片字段（`image_url`、`thumb_url` 等）由后端返回可直接访问的完整 URL（生产为带签名的对象存储地址），客户端展示与下载都直接使用这些 URL 即可，两个由后端代理转发二进制流的接口与该模型重复，且平白占用后端带宽；后端可同时移除对应的流式转发实现。
- **删除 3 个点赞状态查询**：`GET /photos/{id}/like`、`GET /attempts/{id}/like`、`GET /comments/{id}/like`。替代方案：在展示点赞数的响应结构里统一新增布尔字段 `liked`（当前 Session 用户是否已点赞，未登录恒为 `false`），已加到 `PhotoCardBase`（覆盖首页卡片与我的投稿卡片）、图片详情、图片评论列表项、图片作答列表项、`UserAttemptItem`（两个"我的作答"列表及用户某图片作答列表）。设置点赞的 3 个 `PUT` 保留（作答点赞后续改名为 `PUT /solves/{id}/like` 并收窄为仅破解记录可赞，见第 24 节）；其请求 `SetLikeRequest`、响应 `LikeResult` 的点赞状态字段由 `is_like` 统一改名为 `liked`，与卡片/详情的 `liked` 一致（消除同义双名）。
- **删除 `GET /score`（我的积分）**：`GET /user/info` 本就必返 `score_count`，余额从个人信息取；流水仍走 `GET /score/logs`。
- **删除奖品状态、库存单独接口**：`PUT /admin/goods/{id}/status`、`PUT /admin/goods/{id}/stock` 与"更新奖品"`PUT /admin/goods/{id}`（表单本含 `status`、`stock`）完全重叠，改状态或库存直接走更新奖品。
- **删除管理端奖品详情 `GET /admin/goods/{id}`**：其字段与奖品列表项相比只多高清 `image_url`（列表是 `thumb_url`），不值一个接口；已把 `image_url` 补进列表项（必返），编辑/预览直接使用列表数据。`PUT` / `DELETE /admin/goods/{id}` 不变。
- **奖品列表客户端/管理端拆分**：客户端 `GET /goods`（原 `/goods/list`）只返回上架（`in_store`）奖品、无 `status` 参数、无管理员分支；管理端 `GET /admin/goods`（Level ≥ 2）带 `status` 看下架、`keyword` 可按 ID 搜。两端列表项统一为公共 `GoodItem`（`id`、`name`、`description`、`thumb_url`、`image_url`、`score_price`、`stock`、`status`、`created_at`，全必返）、分页 `GoodItemPage`。**`available` 参数从契约删除**（客户端按 `stock` 自行判断可兑换）；旧 `GoodBriefPage` 删除（`GoodBrief` 仍用于兑换记录）。
- **删除奖品详情 `GET /goods/{id}`**：列表项（`GoodItem`）已含详情的全部字段（`description`、高清 `image_url` 等），客户端与管理端详情界面均直接使用列表数据。
- **管理端文案统一**：goods 相关接口的中文名与描述全部由"商品"改为"奖品"（新增奖品、更新奖品、删除奖品等），与客户端叫法一致；字段与 URL 不变。
- **合并用户查询**：删除精确筛选接口 `GET /admin/user`，合并进 `GET /admin/users`（两接口返回字段本就完全一致，均为 `UserSummary`）；合并后统一为单个 `keyword` 模糊搜索 + `status` / `level` 筛选（精确字段的去除见第 17 节）。用户列表与整套用户治理接口一起收归 **Level 3 专用**（见第 4 节），Level 2 不再有任何用户账号入口（工作台数字改由新增的 `GET /admin/stats` 一次性提供，Level ≥ 2 可用：`user_count` 用户总数、`pending_photo_count` 待审核投稿数、`pending_attempt_count` 待审核作答数、`pending_comment_count` 待审核评论数、`pending_feedback_count` 待处理反馈数，全为计数、无任何明细，避免工作台请求多个列表接口凑数字；后续统计字段可扩展）；Level 3 记录仍只读展示。
- **改名**：`GET /admin/users` summary 由"搜索用户"改为"用户列表"（原名是为了与被删的 Level 3"用户列表"区分，合并后不再需要）；调整权限等级接口 summary 由"调整用户权限等级（创世管理员）"缩短为"调整权限等级（创世管理员）"（其 URL 变更见第 15 节）。

保留未合并的（有依据，非冗余）：各作答列表（数据范围与权限不同）；`/score/logs`（余额在 `/user/info`，流水独立分页）。

行为含义：图片的展示与下载统一走 `MediaUrl` 签名地址，URL 失效时按既有约定重新请求业务接口刷新；点赞交互改为渲染时直接读 `liked`、点击走 `PUT`（幂等设置，请求与响应的点赞状态字段统一为 `liked`，响应另含最新 `likes_count`），不再有独立的状态查询请求；用户管理页合并为一个列表页,搜索为单个 keyword 模糊匹配。删除接口属破坏性改动，`liked` 为新增响应字段；两端未上线按可重写对待。

## 13. 活动奖励配置整体下线（字段删除 + 接口删除）

- 从契约中整体删除活动奖励配置：创建/更新活动表单不再接收 `photo_points`、`reward_tiers`（创建表单原必填的 `photo_points` 一并移除）；`ActivityDetail` schema 删除，活动读取统一为 `ActivityCard`。
- 随之删除管理端活动详情 `GET /admin/activity/{id}`：去掉奖励字段后其响应与活动列表项完全一致，详情、编辑界面直接使用列表数据（与奖品详情的处理一致）。
- 两处"奖励隔离规则"说明段落删除；活动时间规则（不得延长已结束活动等）不变。

行为含义：积分发放规则不再按活动逐个配置，退化为后端全局规则（写在配置或代码里，所有活动同一套）；前端本就没有展示奖励配置的界面，管理端创建活动少填两项。积分体系本身（我的积分、流水、兑换）不受影响，只是"发多少分"从契约可配置项变成后端内部规则。属删除字段与接口的破坏性改动，两端未上线按可重写对待。未来若确需按活动差异化奖励，再按契约流程加回。

## 14. 活动列表重构：客户端/管理端两接口

- 删除 `GET /activity/active`（进行中）、`GET /activity/history`（往期）、`GET /admin/activity/list`（管理端旧列表），改为：
  - **客户端 `GET /activity`**（公开）：**只返回进行中（`active`）和已结束（`ended`）活动，不含未开始**；`status` 枚举仅 `active` / `ended`，省略返回两者全部；`keyword` 纯文字、不支持按 ID。响应 `ActivityCardPage`。
  - **管理端 `GET /admin/activity`**（Level ≥ 2）：返回全部活动含未开始（`not_started`）；`status` 三态可筛，`keyword` 可按活动 ID 搜。响应同为 `ActivityCardPage`。
- 未开始活动对客户端完全不可见（列表不返回、题目不下发、不允许投稿作答——后两条为既有活动时间校验）；预告位如需要由管理端安排 `active` 起始时间实现，不靠未开始活动预告。
- 排序统一 `start_time` 倒序、`id` 倒序。`/admin/activity` 另有创建（`POST`）与更新（`PUT /admin/activity/{id}`）写接口。

行为含义：客户端"进行中/往期"两个页签是同一接口传不同 `status`；管理端活动页用 `/admin/activity` 拿含未开始的全量并可按 ID 定位。属删除并重构接口的破坏性改动，两端未上线按可重写对待。

## 15. URL 风格统一（接口改名，行为不变）

按主流 REST 风格统一路径命名，共改名 13 个 operation，方法、参数语义、响应结构均不变（其中 3 个把请求体里的目标 ID 挪进路径）：

| 原路径 | 新路径 |
|--------|--------|
| `GET /photos/list` | `GET /photos`（与上传投稿 `POST /photos` 同路径不同方法） |
| `GET /goods/list` | `GET /goods` |
| `GET /exchange/list` | `GET /exchange` |
| `POST /exchange/claim` | `POST /exchange`（兑换即创建兑换记录） |
| `GET /activity/list` | `GET /activity` |
| `GET /admin/goods/list` | `GET /admin/goods` |
| `POST /admin/goods/new` | `POST /admin/goods` |
| `GET /admin/exchange/list` | `GET /admin/exchange` |
| `GET /admin/feedback/list` | `GET /admin/feedback` |
| `POST /admin/activity/create` | `POST /admin/activity` |
| `POST /admin/activity/update` | `PUT /admin/activity/{id}`（表单字段 `activity_id` 移除，活动 ID 进路径） |
| `POST /admin/exchange/verify` | `PUT /admin/exchange/{id}/verify`（请求体 `exchange_id` 移除，进路径） |
| `PUT /admin/level` | `PUT /admin/users/{id}/level`（请求体 `id` 移除，进路径；与封禁接口 `PUT /admin/users/{id}/status` 形状一致） |

统一规则：列表不带 `/list` 后缀（同路径 GET=列表、POST=创建）；创建/更新不用动词后缀；对单个资源的操作把资源 ID 放路径。ID 进路径后，目标不存在统一按《约定》返回 `404`（`code=5`）。

行为含义：纯改名，不改任何请求/响应字段语义与状态码承诺（除上述三个 ID 从请求体移到路径）。属重命名接口的破坏性改动，两端未上线按可重写对待。

## 16. 新增内容位：弹窗 / 积分规则 / 帮助中心（新增接口）

- 新增单例富文本内容位资源，按 `key` 寻址，共 2 个 operation：`GET /contents/{key}`（公开，未登录可访问）和 `PUT /admin/contents/{key}`（Level ≥ 2，JSON 全量覆盖）。`key` 枚举：`popup`（首屏弹窗）、`score_rules`（积分规则）、`help`（帮助中心）；"关于我们"由前端写死，不进契约。
- `content` 为**纯富文本** HTML 字符串（仅文本类标签，无图片/附件上传），长度按 Unicode 码点（含标签）≤ **5000**（与通知正文同一条"管理员长文 5000"规则），超长 `400`；后端存取时按标签白名单过滤防 XSS。未编辑过的内容位返回 `content=""`、`version=0`、`updated_at=null`。
- **版本防打扰**：每次后台保存 `version` 自增。弹窗关闭后由前端本地记录已关闭的 `version`，仅当版本增大才重新弹出；**服务端不记录任何用户的关闭状态**（不需要 dismiss 表）。
- **弹窗关联引导**：`popup` 可选 `related_id` 关联一条通知（保存时通知不存在返回 `400`，省略即清除；其他 `key` 提供该字段 `400`）。前端流程：未登录用户可见弹窗，点"查看详情"请求通知详情得 `401`，前端引导登录后跳转；已登录直接跳转。
- schema 新增 `ContentBlock` / `UpdateContentRequest`。均为新增接口，非破坏性。

行为含义：弹窗、积分规则、帮助中心都是"后台改一段富文本"的静态内容位，统一资源避免三套接口；弹窗的打扰控制完全在客户端本地，后端只负责版本号递增。

## 17. 用户列表搜索简化为单 keyword（参数删除）

- `GET /admin/users` 删除 `netid` / `name` / `nickname` 三个精确匹配参数，只保留一个 `keyword`：后端对**用户 ID、学号（netid）、姓名（username）、昵称（nickname）**做 OR 模糊匹配（`ILIKE`），最长 50；与其他管理端列表一致，均支持按记录 ID 搜索。
- 依据：三个精确参数与 `keyword` 模糊搜索职能重叠，且"前端把同一个值复制进三个精确字段模拟搜索框"会把查询结构泄漏到前端、并非主流做法；单 `keyword` 模糊 OR 才是统一搜索框的标准形态，参数更少、支持部分匹配、后端一条查询。用户量千级，模糊匹配无索引的性能顾虑不成立。
- **客户端搜索一律不支持按 ID（业务 ID 与数据库 ID 均不可）**，仅按文字字段模糊匹配；各接口支持的具体字段已在《约定》"客户端搜索""管理端搜索字段"两条逐一列明。属删除参数的破坏性改动，两端未上线按可重写对待。

## 18. 管理端列表搜索分类（新增 user_keyword）

管理端列表的搜索**按被引用实体拆为独立关键词**：主 `keyword` 只搜列表自身实体，被引用的"人"走 `user_keyword`、被引用的"题目"走 `photo_keyword`（沿用兑换列表 `user_keyword` / `good_keyword` 既有模式）。各关键词均可选、AND 组合、各 ≤50、OR 匹配各自字段。

| 接口 | `keyword`（自身） | `photo_keyword`（题目） | `user_keyword`（人） |
|------|------------------|------------------------|----------------------|
| `GET /admin/photos` | 题目 ID / 标题 / 描述 | —（自身即题目） | 作者 ID / 昵称 |
| `GET /admin/attempts` | 作答 ID | 题目 ID / 题目标题 | 作答者 ID / 昵称 |
| `GET /admin/comments` | 评论 ID / 评论内容 | 题目 ID / 题目标题 | 评论者 ID / 昵称 |
| `GET /admin/feedback` | 反馈 ID / 标题 / 内容 | —（不引用题目） | 提交者 ID / 昵称 |

- 变化点：原先混在 `keyword` 里的"作者/用户""所属题目"字段全部拆到 `user_keyword` / `photo_keyword`；`/admin/attempts` 为净新增按作答者、按题目搜索的能力。
- 单实体、无引用维度的列表（活动、奖品、通知、用户、反馈的题目维度）不拆对应参数。
- 属既有可选参数语义调整（`keyword` 范围收窄）+ 新增可选参数，两端未上线按可重写对待。

## 19. 反馈附件支持视频（字段改名 + 放宽校验）

- 提交反馈 `POST /feedback` 的附件字段由 `image_file1-3` 改名为 **`media_file1-3`**（仍最多 3 个），每个附件可为图片（jpg/png，≤20MB）或**视频（mp4/mov，≤50MB）**；类型或大小不符返回 `400`。
- 反馈详情 `medias[].media_type` 定义枚举：`1` 图片、`2` 视频（此前只有图片、未声明枚举）。附件 `url` 沿用媒体 URL 签名规则，视频同样由后端返回可直接访问的完整地址。
- 《约定》"上传文件"条目同步拆分：其余上传位（头像、封面、题目、作答、通知配图、奖品图）仍仅支持图片；反馈附件是唯一支持视频的上传位。

行为含义：反馈场景常需要录屏复现问题，只加在反馈一处，不放开其他上传位，控制存储与转码成本。属字段改名（破坏性）+ 放宽校验，两端未上线按可重写对待。

## 20. 契约一致性清理（命名统一 + 声明补全，行为不变）

发交接前的整体体检,统一若干残留的风格分叉:

- **点赞状态字段统一 `liked`**：`SetLikeRequest`、`LikeResult` 的 `is_like` 改名为 `liked`，与卡片/详情响应的 `liked` 一致，全契约点赞状态只有一个字段名（详见 §13）。
- **工作台统计字段 `_total` → `_count`**：`GET /admin/stats` 的 `user_total` 等 5 个字段改为 `user_count` / `pending_photo_count` / `pending_attempt_count` / `pending_comment_count` / `pending_feedback_count`，与既有 `likes_count` / `unread_count` / `solved_count` 等计数字段统一后缀；分页 `total` 语义独立、不受影响。
- **管理端 operationId 统一 `admin` 前缀**：`reviewPhoto` / `reviewAttempt` / `reviewComment` → `adminReviewPhoto` / `adminReviewAttempt` / `adminReviewComment`；`adminSearchUsers` → `adminListUsers`（与 `adminList*` 系列及"用户列表"命名一致）。仅 operationId（代码生成标识）变化，URL、参数、响应均不变。
- **补齐 5 个写接口的 `400` 声明**：`PUT /photos|solves|comments/{id}/like`、`PUT /admin/feedback/{id}`、`PUT /admin/exchange/{id}/verify` 的请求体含必填/枚举字段，补上请求体非法时的 `400`（`StandardErrorResponse`），使 `responses` 覆盖完整。属新增错误声明,非破坏性。

## 21. 题目计数模型重构：作答数 / 破解数 / 个人破解分离

区分之前混淆的两个数，并把"是否破解"拆成个人与全局两个概念，与点赞对称：

| 概念 | 个人（当前用户） | 全局 |
|------|-----------------|------|
| 点赞 | `liked`（bool） | `likes_count`（int） |
| 破解 | `solved`（bool，重定义） | `solved_count`（int，破解数） |
| 作答 | `user_attempts_count`（int，我的作答数） | `attempts_count`（int，全局作答数） |

- **旧 `solved`（bool，含糊的"是否已被破解"）删除**；改为 `solved_count`（破解数，`status=solved` 的作答数）+ `attempts_count`（作答数，提交作答次数），两者在题目卡片、图片详情、我的投稿卡片/详情、管理端题目列表统一返回（管理端本就有，其余补齐）。
- **`solved` 重定义为个人布尔**："当前用户是否已破解此题"，与 `liked` 对称；最终**仅在图片详情返回**（§28 已将其从浏览卡片 `PhotoCard` 移除）。**我的投稿卡片/详情不含**（作者不破解自己的题）。未登录恒为 `false`。
- **新增个人作答次数 `user_attempts_count`**：题目详情 `GET /photos/{id}` 增加 `user_attempts_count`（当前用户在该题上的已作答次数；未登录恒为 `0`），方便详情页直接渲染个人作答次数与破解状态。
- **`solved` 筛选参数**：最终仅 `GET /photos`（浏览）与 `GET /admin/photos` 保留，语义均为**全局**（`true` = 破解数 > 0，见 §42）；`GET /photos/user`（我的投稿）不设该筛选（§28 移除）。

## 22. 图片下读取接口重构（作答成功 / 我的作答 / 评论）

图片（Photo）下的三个读取接口职责厘清：

- **作答成功列表 `GET /photos/{id}/solves`**（原"图片作答列表 `GET /photos/{id}/attempts`"）：公开，**只返回破解成功（`status=solved`）的作答**，按破解时间倒序，是"谁破解了此题"的展示；列表项去掉原来每条的 `solved` 布尔（全部已破解，冗余），去掉 `sort_by`（固定时间倒序）。路径由 `attempts` 改为 `solves`——只展示成功破解，`attempts`（尝试）名不副实；`POST /photos/{id}/attempts`（提交作答）与 `GET /photos/{id}/attempts/user`（我的作答，含全部尝试）仍用 `attempts`。
- **我在本图的作答 `GET /photos/{id}/attempts/user`**（原"用户某图片作答列表"）：登录用户看自己在本题的全部作答，去掉 `status` 筛选和 `sort_by`（固定时间倒序）；每条仍含本人作答的 `status`（自己可见判定结果）。
- **图片评论列表 `GET /photos/{id}/comments`**：不变。

配套的三个"我的"全局记录接口保持：我的作答记录 `GET /attempts/user`、我的投稿记录 `GET /photos/user`、我的投稿详情 `GET /photos/user/{id}`（后两者 summary 由"列表"改为"记录"，仅展示名）。

行为含义：公开面只展示成功破解（不泄漏失败猜测、不逐条暴露判定），个人面看自己的全部作答与判定；作答数与破解数是两个独立指标，个人是否破解与全局破解数分离。均属响应字段与查询参数调整，两端未上线按可重写对待。

## 23. URL 规范统一（"我的"资源与破解列表）

- **我的投稿详情 `GET /photos/review/{id}` → `GET /photos/user/{id}`**：与"我的投稿记录 `GET /photos/user`"同前缀，遵循全库"我的 X = `/X/user`"后缀约定（另有 `/attempts/user`、`/photos/{id}/attempts/user`）；`review` 前缀是唯一的例外，去除。
- **作答成功列表 `GET /photos/{id}/attempts` → `GET /photos/{id}/solves`**：路径反映"只返回破解成功"的语义（见 §22）。
- 其余 URL 复核一致：集合/单项 `/X` + `/X/{id}`；单项动作 `/X/{id}/action`（`like`/`review`/`status`/`level`/`verify`）；管理端一律 `/admin/X`。无其他不一致。

## 24. 点赞范围收窄 + 客户端章节重分类

**点赞模型定稿**：可点赞对象全库仅三类——**题目、破解记录、评论**，对应 `PUT /photos/{id}/like`、**`PUT /solves/{id}/like`**（原 `PUT /attempts/{id}/like` 改名，`{id}` 仍为作答 ID，但仅对破解记录即 `status=solved` 的作答有效，其余返回 `404`）、`PUT /comments/{id}/like`。配套字段调整：

- `PhotoCardBase` 拆分：`likes_count` / `liked` 移入浏览面的 `PhotoCard` 扩展；**我的投稿卡片（`UserPhotoCard`）、我的投稿详情、`UserAttemptItem`（我在本图的作答 / 我的作答记录）不再返回任何点赞字段**——个人记录只看内容与判定，点赞发生在公开面。
- 我的投稿记录、我的作答记录删除 `sort_by` 参数（原可按 `likes_count` 排序，点赞字段移除后失去意义），固定活动分段 + 段内 `created_at` 倒序。
- 《约定》新增"点赞范围"条目；`LikeResult` / `SetLikeRequest` 描述同步。

**客户端章节重分类**（对齐管理端的资源式分组，同步 OpenAPI tags）：

| 章节 | 接口 |
|------|------|
| 图寻题目 | 图片列表、图片详情、上传投稿、设置题目点赞状态 |
| 作答 | 提交作答、破解记录、我在本图的作答、设置破解点赞状态 |
| 评论 | 评论列表、发表评论、删除评论、设置评论点赞状态 |
| 我的记录（新增章节） | 我的投稿记录、我的投稿详情、我的作答记录 |

**术语统一**：全部文档"作答"替代"答题"（作答 = attempt 实体，一次猜测提交；破解 = `status=solved` 的作答，非独立实体），管理端相关接口中文名同步（管理端作答列表、审核作答等）。属字段删除 + 接口改名的破坏性改动，两端未上线按可重写对待。

## 25. 作用域内冗余关联清理（列表项按作用域拆分）

嵌套关联对象的规则定稿：**跨资源聚合列表带被引对象摘要（避免前端 N+1 逐条查询），资源作用域内的列表不重复返回父对象**（父对象已在 URL 与页面上下文中）。

- **我在本图的作答 `GET /photos/{id}/attempts/user`**：列表项不再返回 `photo` 摘要对象，改用新公共基底 `AttemptRecordBase`（`id`、`status`、`reject_reason`、`created_at`）。
- **破解记录 `GET /photos/{id}/solves`**与**题目评论列表 `GET /photos/{id}/comments`**：列表项删除 `photo_id`（题目已由路径限定，不重复返回冗余父对象 ID）。
- **我的作答记录 `GET /attempts/user`**：保留题目摘要——`UserAttemptItem` 重构为 `AttemptRecordBase` + 必返 `photo`（`PhotoBrief`：`id`、`title`、`thumb_url`、`activity`），跨题目聚合列表展示题目图片、标题及所属活动，不再返回作答本身的图片与坐标。
- schema：新增 `AttemptRecordBase`；`UserAttemptItem` 改为 allOf 组合。属删除响应字段的破坏性改动，两端未上线按可重写对待。

> 注：本节 schema 名与结构为当时中间态。最终以 §42 为准：`AttemptRecordBase` → `AttemptRecord`（并补回缩略图 `thumb_url` 与 `location`）、`UserAttemptItem` → `UserAttemptCard`（独立结构，非 allOf）、`PhotoBrief` 去掉 `activity`（仅 `id`、`title`、`thumb_url`）。

## 26. 作答业务规则：作者自答/已破解成功/作答次数达上限禁止再次作答

- 提交作答 `POST /photos/{id}/attempts` 校验规则扩展：
  1. **题目作者不能作答自己投稿的题目**，违反返回 `400`（`code=5`）；
  2. **已破解成功（`status=solved`）的题目禁止再次作答**，违反返回 `400`（`code=5`）；
  3. **作答次数达到上限（`user_attempts_count` 达到单题允许最大次数）后禁止再次作答**，违反返回 `400`（`code=5`）。
- 连带自洽：个人破解状态 `solved` 与"我在本图的作答"对题目作者恒为空/false；管理员官方账号发布的题目不受影响（普通用户均可作答）。

## 27. 我的投稿详情收窄为非公开态（字段/枚举删除）

- 我的投稿详情 `GET /photos/user/{id}` **仅服务审核中（`pending`）与已驳回（`rejected`）投稿**：`status` 枚举由 `pending/approved/rejected` 收为 `pending/rejected`；已通过（`approved`）投稿即公开题目，走公开的 `GET /photos/{id}`，对 approved / 他人 / 不存在的请求本接口一律返回 `404`。
- 非公开投稿不可被作答，故详情**删除 `attempts_count` / `solved_count`**（恒为 0，无意义）。
- **我的投稿记录（列表 `GET /photos/user`）不变**：仍返回全部状态，已通过行的 `attempts_count` / `solved_count` 有意义；前端对已通过行跳公开图片详情、对 pending/rejected 行跳本详情接口。
- 属删除响应字段 + 收窄枚举的破坏性改动，两端未上线按可重写对待。

## 28. 题目卡片瘦身（列表只保留卡片必需字段）

浏览与个人列表的题目卡片精简为"卡片身份"字段,把仅详情展示或成本较高的字段从列表移除:

- **`PhotoCardBase` 收敛为 `id`、`activity`、`title`、`thumb_url`、`created_at`**——删除 `description`（简介进图片详情/投稿详情看）、`attempts_count`、`solved_count`（作答数/破解数只在图片详情展示，作者看自己题目也走公开详情）。
- **浏览卡片 `PhotoCard` 删除个人 `solved`**：判断"当前用户是否破解"需按（用户,题目）逐卡查询、无法反规范化，成本最高且列表不展示；个人破解态只在图片详情返回。浏览卡片保留 `likes_count` / `liked`（卡片展示点赞）。
- **删除 `solved` 筛选参数**：客户端图片列表 `GET /photos`、我的投稿记录 `GET /photos/user` 去掉按破解状态筛选（可有可无）；管理端题目列表 `GET /admin/photos` 保留 `solved` 筛选（审核场景）。
- `attempts_count` / `solved_count` 现仅存于**图片详情 `GET /photos/{id}`**（公开，含个人 `solved`）与**管理端题目列表 `AdminPhotoListItem`**（审核）；`description` 仅存于图片详情、投稿详情、管理端题目列表。
- keyword 仍可按后端 `description` 列模糊搜索（字段从卡片响应移除 ≠ 后端无此列）。属删除响应字段与查询参数的破坏性改动，两端未上线按可重写对待。

## 29. 列表作答图统一改用缩略图（字段改名 `image_url` → `thumb_url`）

列表项一律只返回缩略图，高清原图只在详情接口出现。此前三个客户端作答/破解列表仍以高清图作为列表展示图，本轮统一改为缩略图:

- **我在本图的作答 `GET /photos/{id}/attempts/user`**、**我的作答记录 `GET /attempts/user`**:公共基底 `AttemptRecordBase` 的猜测图字段 `image_url` 改名为 `thumb_url`（语义由高清原图变为缩略图）;`UserAttemptItem` 经 allOf 复用该基底，随之改变。
- **破解记录 `GET /photos/{id}/solves`**:内联列表项的猜测图字段 `image_url` 同样改名为 `thumb_url`。
- **未受影响**:图片详情 `GET /photos/{id}`、我的投稿详情 `GET /photos/user/{id}` 等详情接口保留高清 `image_url`;管理端题目列表 `AdminPhotoListItem`、管理端作答列表本就同时返回 `thumb_url`（列表展示）+ 高清 `image_url` / `guess_image_url`（审核放大,二者均无独立详情接口作为高清来源）,保持不变;奖品列表 `GoodItem` 的 `thumb_url` + 高清 `image_url`（供编辑/预览,无奖品详情接口）不变。

属响应字段改名的破坏性改动,两端未上线按可重写对待。

## 30. 个人记录模型微调：投稿记录增加状态筛选 & 作答记录瘦身（与提交前相比）

与提交前相比，对客户端个人记录接口做出如下调整：

1. **我的投稿记录 `GET /photos/user` 新增 `status` 筛选、移除 `reject_reason` & 排序规则调整**：增加可选 Query 参数 `status=pending|approved|rejected`；从 `UserPhotoCard` 移除 `reject_reason`（由“我的投稿详情 `GET /photos/user/{id}`”提供）；列表按投稿时间 `created_at` 倒序、记录 `id` 倒序返回扁平列表。
2. **我的作答记录 `GET /attempts/user` 状态语义明晰与约束**：`UserAttemptItem` 的 `status` 明确为当前用户在该题上**最新一次作答的判定状态**（`pending` / `solved` / `unsolved`）；`UserAttemptItem` 移除作答猜测图 `thumb_url`、猜测坐标及 `reject_reason`，新增该题我的已作答次数 `user_attempts_count`；列表按作答时间 `created_at` 倒序、`id` 倒序返回扁平列表。
3. **题目列表/瀑布流 `GET /photos` 移除 `activity` 字段**：`PhotoCardBase`（题目卡片基底，供 `PhotoCard` 与 `UserPhotoCard` 继承）移除关联活动 `activity` 对象，精简瀑布流卡片传输数据；题目所属活动保持在“题目详情 `GET /photos/{id}`”中完整返回。
4. **全站题目检索扩展 `GET /photos`**：当不指定 `activity_id` 时，默认涵盖所有进行中与已结束活动的题目（未开始的除外），前端直接传入 `keyword` 即可全局搜索往期题目，无需额外增设控制参数。

## 31. 新增公共错误响应 schema `StandardErrorResponse`

新增公共 schema `StandardErrorResponse`（继承 `ErrorResponseBase`、`resp` 固定为 `null` 的标准错误响应），供各接口本轮补齐的 `400`/`429` 等错误声明统一引用，无业务字段含义变化。operation 总数与最终一致性校验结果见文末 §45。

## 32. 业务边界校验规则显式化补充

1. **题目评论与点赞边界**（`POST /photos/{id}/comments` 与 `PUT /photos/{id}/like`）：只能对审核通过（`status=approved`）且所属活动为进行中或已结束的题目发表评论与点赞；未审核、已驳回或尚未开始活动的题目操作拦截返回 `400`（`code=5`）；评论正文限制在 1~140 个字符。
2. **破解点赞边界**（`PUT /solves/{id}/like`）：只能对破解成功（`status=solved`）的作答记录点赞；对待审核或判定未破解的作答点赞拦截返回 `400`（`code=5`）。
3. **积分兑换边界**（`POST /exchange`）：已下架奖品（`out_store`）、剩余库存不足（`stock < quantity`）或可用积分不足（`score_count < score_cost`）拦截返回 `400`（`code=5`）；强制校验 `Idempotency-Key` 请求头。
4. **前台评论删除权限**（`DELETE /comments/{id}`）：仅允许评论作者本人删除自己的评论，非作者（含管理员）在前台试图删除他人评论均返回 `403`；管理员下架/处理违规评论统一通过后台管理接口 `PUT /admin/comments/{id}/review` 操作。
5. **提交反馈限制**（`POST /feedback`）：正文限制在 1~500 个字符；附件最多 3 个（图片 ≤ 20MB / 视频 ≤ 50MB），超出限制拦截返回 `400`（`code=5`）。
6. **管理端奖品删除保护**（`DELETE /admin/goods/{id}`）：已有用户兑换记录的奖品禁止物理删除，仅可进行下架（`out_store`）处理，强制物理删除拦截返回 `400`（`code=5`）。
7. **管理端活动时间约束**（`POST /admin/activity` 与 `PUT /admin/activity/{id}`）：活动开始时间必须早于结束时间（`start_time < end_time`）；已结束活动禁止篡改其时间基准，违反拦截返回 `400`（`code=5`）。
8. **创世管理员权限保护**（`PUT /admin/users/{id}/status` 与 `PUT /admin/users/{id}/level`）：仅创世管理员（Level 3）可调用，且禁止对任意 Level 3 创世管理员账号进行封禁或等级调整，违反拦截返回 `403`。

## 33. 文档结构优化：全局通用约定与单接口业务规则分工明晰

- **全局通用约定（文档顶部 `## 约定` 节）**：仅保留跨全站接口复用的通用协议（基础路径 `/api`、`snake_case` 命名、`success/resp/message/code` 响应结构、ISO 8601 时区时间、`list/total` 分页规范、媒体 URL 不透明规则及 404/400 通用规范）。
- **单接口专有业务规则**：各接口专属的校验逻辑（如反馈正文 500 字与 3 个附件限制、作答四连约束、点赞范围、奖品物理删除保护等）全部完整下沉并收拢至各自具体接口段落中，不混入全局约定，便于单接口对照查阅。

## 34. 兑换记录奖品摘要 `GoodBrief` 精简：移除冗余 `stock` 字段

- 兑换记录列表（`GET /exchange` 与 `GET /admin/exchange`）返回的是历史账单记录，其嵌套的奖品摘要 `GoodBrief` 仅用于渲染历史兑换卡片（`id`、`name`、`thumb_url`、`score_price`）。
- 实时库存 `stock` 仅在奖品列表（`GET /goods` / `GET /admin/goods`）中有意义；已从 `GoodBrief` 摘要模型中移除 `stock` 字段，精简传输数据并消除历史列表对当前奖品库存表的关联成本。

## 35. 互动消息 `InteractionMessage` 交互重构：精细化单条已读 + 标记接口扩展

- **单条已读标记**：`InteractionMessage` 保留 `is_read: boolean` 字段。客户端拉取 `GET /notifications` 时后端**不自动清空**未读状态，支持单条卡片独立渲染未读高亮或蓝点，并精准支持点击卡片跳转到关联对象（题目 `photo` / 破解记录 `solve` / 评论 `comment`）。
- **新增标记已读接口**：
  1. `PUT /notifications/{id}/read`：标记单条互动消息已读（点击卡片跳转时调用）；
  2. `PUT /notifications/read-all`：一键标记全部互动消息已读（用于消息列表一键清空未读数/小红点）。
- **普通通知区分**：普通通知/公告（`GET /announcements/{id}`）拥有独立详情页，用户点击请求通知详情时由后端自动将其标记为已读，不需额外设置标记接口。

## 36. 地理坐标聚合优化：统一收拢为公共 `Location` 对象

- **聚合封装**：原离散的 `longitude`（经度）、`latitude`（纬度）、`coord_type`（坐标系）三个孤立字段统一聚合成公共 Schema **`Location`** 对象（定义在 `components.schemas.Location`）。
- **应用范围**：
  1. **题目详情 `GET /photos/{id}`**：答案坐标由原离散三字段聚合为 `"location": Location | null`（进行中/未开始活动固定返回 `null`）；
  2. **作答记录项 `AttemptRecord`**：作答猜测坐标由原离散三字段聚合为 `"location": Location`；
  3. **我的投稿详情 `GET /photos/user/{id}`**：投稿坐标由原离散三字段聚合为 `"location": Location`；
  4. **管理端题目/作答列表**：题目坐标与猜测坐标统一聚合为 `"location": Location`、`"guess_location": Location`、`"photo_location": Location`。
- **优点**：提升数据内聚性，与其他实体（`user`、`activity`）风格高度一致；活动未结束防泄密时整块返回 `"location": null` 语义更加干净利落。

## 37. 管理端列表结构标准化改造（`GET /admin/attempts` 与 `GET /admin/comments`）

- **统一标准主键名**：清除全站响应体中残存的非标主键字段，原 `attempt_id` 与 `comment_id` 统一更名为标准主键字段名 **`id`**。
- **关联题目快照封装**：
  1. **作答列表 `GET /admin/attempts`**：关联题目的 `photo_id`、`photo_title`、`thumb_url`、`location` 统一聚合成干净嵌套的 **`photo`** 对象（`id`、`title`、`thumb_url`、`location`）；
  2. **评论列表 `GET /admin/comments`**：关联题目的 `photo_id`、`photo_title` 统一聚合成干净嵌套的 **`photo`** 对象（`id`、`title`），评论正文更名为标准的 **`content`**。
- **全站扫描结果**：经全量代码扫描，全站所有实体响应已 100% 消除 `xxx_id` 主键杂音，所有主键统一为 `id`，关联对象统一下发嵌套实体快照。

## 38. 作答判定机制与生命周期定稿

契约此前未说明作答如何被判定，本轮明确：

- **判定＝坐标自动 + 图片人工**：作答提交后，后端按猜测坐标与题目答案坐标的**距离阈值（默认 50 米，后端可配置）**自动判定坐标是否命中；提交的现场实拍猜测图片由管理员人工审核。新作答初始 `status=pending`，管理员在 `PUT /admin/attempts/{id}/review` 结合坐标命中与图片有效性确认为 `solved` / `unsolved`。
- **作答判定为终态（双向锁定）**：管理员把 `pending` 作答判为 `solved` 或 `unsolved` 后**不可再改判**，`solved`↔`unsolved` 两个方向都不允许，对已判定作答再次审核返回 `409`；因此不存在破解数/积分的回退逻辑。作答判为 `solved` 时更新该题 `solved_count` 与作答者积分（reason `answer_correct`）。
- **单题作答次数上限 = 5**：每人对同一题目最多作答 5 次（`user_attempts_count` 上限 5），达上限再次提交返回 `400`/`code=5`。此前契约提到"上限"却无数值，现定为 5。
- **题目审核为终态（双向锁定）**：`pending` 题目审核为 `approved` 或 `rejected` 后**不可再改判**，两个方向都不允许，重复审核已决题目返回 `409`；被驳回题目不能通过审核或编辑恢复公开。
- **仅评论审核可反复改判**：评论 `approved`↔`rejected` 可随时切换、不返回 `409`（作答与题目审核均为终态，唯评论例外）。

## 39. 管理端通知已读人数 `read_count`（拆分管理端通知 schema）

- 管理端通知列表 `GET /admin/announcements` 与详情 `GET /admin/announcements/{id}` 不再复用客户端 schema，改用新 schema **`AdminAnnouncementPage` / `AdminAnnouncementListItem` / `AdminAnnouncement`**：去掉面向用户的 `is_read`（列表项）与 `unread_count`（页级），改为每条返回聚合已读人数 **`read_count`**（已读该通知的去重用户数），供运营查看触达效果。客户端 `/announcements` 系列不变。
