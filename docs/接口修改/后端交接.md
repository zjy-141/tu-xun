# 后端交接（本次接口契约改动）

**总量**：operation 由提交前的 **68** 增加到 **72**：新增 7 个 operation（4 个新写接口、3 个改名后的列表接口），移除 3 个旧的 `/pending` 列表 operation，净增 4。3 条旧 URL 及其 `operationId`（`listPendingPhotos`、`listPendingAttempts`、`listPendingComments`）属于破坏性重命名；两端尚未上线，按可重写处理。`check_contract.py` 通过。

## 1. 活动题目：新增写接口 + 读取升级为统一题目池

- **新增 2 个 operation**（表单 `AdminPhotoUpsertForm`，`multipart/form-data`）：
  - `POST /admin/activity/{activity_id}/photos`：管理员在任意活动阶段新增题目，新增后直接 `approved`；作者规则本轮由「记为当前管理员」改为「**固定记为官方账号**」（见下）。
  - `PUT /admin/activity/{activity_id}/photos/{photo_id}`：编辑题目内容，不改变审核状态；编辑 `rejected` 题目也不会重新进入审核或恢复公开；至少提交一个字段，改坐标时 `longitude/latitude/coord_type` 必须成组提交。
- **`GET /admin/photos/pending` 改名为 `GET /admin/photos`，并升级为管理端唯一题目列表 / 全局题目池**：旧名会把它误导成“只查待审核”，实际返回全部活动、全部审核状态（`pending/approved/rejected`）的未删除题目，故去掉 `/pending` 后缀。本轮为其新增两个可选参数：`activity_ids`（重复参数 `activity_ids=1&activity_ids=2`，多个活动 ID 之间 OR）和 `keyword`（题目 ID、标题、描述、作者 ID 或昵称，≤50），与 `status` 按 AND 组合。列表项 schema 改为 `AdminPhotoListItem`，新增所属活动 `activity`（`ActivityBrief`，仅 `id`、`title`）。

行为含义：管理端只有一个跨活动、可多活动筛选的题目列表查询；不提供按单个活动读取题目的接口。旧 `/admin/photos/pending` 不再作为契约路径。

行为含义（作者规则）：官方账号是部署侧预置的一条真实用户记录（昵称如“图寻官方”），管理端新增题目时 `photos.user_id` 固定写入该账号；客户端和管理端各接口返回的 `author` 就是该账号的 `UserBrief`，契约不新增渠道字段。运营以个人身份投稿仍走 `POST /photos` 普通流程、正常审核、入库本人 ID。实际操作的管理员是谁属于后端内部审计需求，如需记录由后端自行加内部字段，不进契约。

- 题目**暂不提供删除接口**（`DELETE .../photos/{photo_id}`）：审核为一次性、编辑接口已可修正内容问题，故先只支持新增/编辑。代价是已通过题目暂时只能改内容、无法整体下架或隐藏；未来确有下架需求时再补 `DELETE`（或把审核改为可重复以支持 approved→rejected 撤下）。

## 2. 通知：新增编辑/删除接口 + 读取复用客户端

- **通知新增图片能力（含一处破坏性改动）**：`POST /admin/notifications` 请求由 `application/json` 改为 `multipart/form-data`（内容类型变更，属破坏性改动），`CreateNotificationRequest` 新增可选 `image_file`；`Notification` schema 新增可选 `image_url`，通知详情与当前全局公告接口在有图时返回、无图时省略该字段。互动消息不支持图片。
- **新增 2 个 operation**（与发布接口一致，均 `multipart/form-data`）：
  - `PUT /admin/notifications/{id}`（`UpdateNotificationRequest`）：编辑管理员发布的 `category=normal` 通知；未提供字段保持不变；`remove_image=true` 移除图片、`remove_relation=true` 移除活动关联（两个开关分别不能与对应新值同传）；切换类型时后端自动清理不兼容字段（切全局公告须提供新 `expires_at`，切一般通知清除 `expires_at`）；编辑不重置用户已读状态。
  - `DELETE /admin/notifications/{id}`：删除后不再出现在客户端通知列表和全局公告候选中。互动消息不能通过本接口编辑或删除。
- **管理端读取不新建 `/admin` 接口**：列表复用 `GET /notifications`（固定 `category=normal`，按需带 `type`、`keyword`、分页），详情复用 `GET /notifications/{id}`。

行为含义：`normal` 通知是面向全部登录用户的全局发布记录，Level 2/3 用 `category=normal` 查询即可读到全部未删除记录（含早于该管理员账号创建时间的记录），因此读取无需单建 `/admin` 接口，只有写入走 `/admin`。列表里的 `is_read` 始终是当前请求账号自己的已读态。

## 3. 通知列表改为正文预览 `content_preview`（字段级改动）

- 客户端 `GET /notifications` 列表项从完整 `Notification` 改为 `NotificationListItem`，固定只返回 `id`、`category`、`type`、`title`、`content_preview`、`is_read`、`created_at`，**不再返回完整 `content`、`image_url`、关联对象或发送者字段**。
- `content_preview` 由后端从完整 `content` 生成，规则固定：① 将字面量 `[image]` 占位标记替换为空格；② 合并换行/制表符/连续 Unicode 空白为一个半角空格并去首尾；③ 按 Unicode 码点截取前 50 个字符，不加省略号，清洗后为空返回空字符串。
- `keyword` 仍匹配原始完整正文，不对 `content_preview` 搜索；详情 `GET /notifications/{id}` 仍返回完整 `content`，并返回本轮新增的可选 `image_url`（见 §2）。

行为含义：列表不再下发完整正文，避免为生成摘要而逐条读取详情和下载大正文；完整正文和图片只在详情接口返回。

## 4. 管理端搜索与筛选（本轮补充/明确的字段）

- 统一题目池：新增 `activity_ids`、`keyword`（见 §1）。
- 答题审核、评论审核列表：路径由 `/admin/attempts/pending`、`/admin/comments/pending` 改名为 `/admin/attempts`、`/admin/comments`（与统一题目池一致，去掉误导性的 `/pending` 旧名），默认改为返回全部状态、`pending` 降为 `status` 筛选值；本轮另新增 `keyword`。答题列表返回猜测坐标的 `guess_coord_type` 和题目答案坐标的 `coord_type`；评论列表每条记录返回当前 `status`，不能用筛选条件推断混合结果中的单条状态。
- 活动列表：新增 `keyword`（活动 ID、标题或描述）与 `status=not_started|active|ended`（后端按服务器当前时间计算）。
- 商品列表的 `keyword` 语义明确为按商品 ID、名称或描述搜索；兑换列表新增 `exchange_id`、`user_keyword`、`good_keyword`；反馈列表新增 `keyword`；`/admin/users` 与 Level 3 专用 `/admin/user` 新增 `status`、`level` 筛选，专用接口的 `netid`、`name`、`nickname` 精确参数统一 ≤50。字符串搜索参数一律 ≤50，搜索与筛选同时提供按 AND 组合。

## 5. 权限等级与账号状态模型（本轮细化）

- 术语：文档统一把“超级管理员”改为“**创世管理员**”，由部署侧管理、可存在多个；同时明确 Level 3 只能由部署侧治理，业务接口不再把未登录或 Level 0 当作用户账号等级。
- **登录态、权限等级、账号状态三者相互独立**：未登录只是当前请求没有有效 Session，不写用户表、也不把 `level` 记为 0；账号 `level` 只允许 `1/2/3`，`status` 独立为 `active/banned`；封禁/解封不改 `level`，调级不改 `status`。

| 操作者 | 可封禁 / 解封 | 可调整等级 |
|-------|---------------|------------|
| Level 2 | 仅 Level 1 | 无 |
| Level 3 | Level 1、Level 2 | Level 1、Level 2 之间调整 |

- `PUT /admin/users/{id}/status` 由 Level 2/3 共用；Level 2 操作 Level 2/3、任何人操作 Level 3 时返回 `403`（`code=7`）；封禁后立即吊销目标全部 Session。
- `PUT /admin/level` 仅 Level 3 可调用，`target_level` 只允许 `1` 或 `2`；Level 3 之间不能互相治理，也不能治理自己。Level 3 的创建/修改/删除及状态、等级变更只能走部署侧受控流程，业务用户列表只读展示其摘要。

## 6. 文本字段长度统一定稿（字段级收紧）

请求侧文本字段长度本轮全部定稿，均按 Unicode 码点计数，超长返回 `400`；相关 operation 的 `responses` 已补齐 `400` 声明；`api.md`《约定》保留标题统一条目，其余在各接口参数表逐字段标注。原值 → 现值：

| 字段 | 原值 | 现值 |
|------|------|------|
| 所有 `title`（题目 / 活动 / 通知 / 反馈） | 无上限 / 255 / 128 / 100 | **20** |
| 昵称 `nickname`（`PUT /user/info`） | 20 | **10** |
| 题目描述 `description`（投稿、管理端题目表单） | 无上限 | **50** |
| 活动描述 `description`（创建 / 更新活动） | 无上限 | **100** |
| 商品名称 `name`（`GoodUpsertForm`） | 50 | **20** |
| 商品描述 `description`（`GoodUpsertForm`） | 500 | **50** |
| 通知正文 `content`（发布 / 更新通知） | 无上限 | **2000** |
| 驳回原因 `reject_reason`（图片 / 评论审核 `ReviewActionRequest`、答题审核） | 无上限 | **50** |
| 评论 `comment_text` | 500 | **140** |
| 反馈内容 `content` | 500 | 500（不变） |
| 反馈联系方式 `phone` | 20 | 20（不变） |
| 列表搜索 `keyword`（全站） | 50 | 50（不变） |

属于收紧校验（破坏性改动），两端均未上线，按可重写对待，无需过渡方案。

附带修正：`POST /photos` 与 `POST /photos/{id}/attempts` 的 `coord_type` 此前只在描述里写了 `wgs84/gcj02/bd09` 而未声明 `enum`（管理端表单已有），本轮补上 enum，使 spec 与既有文字一致，合法取值不变。

行为含义：标题、商品名是卡片单行位，20 字防溢出；题目/商品描述是卡片两三行位，50 字；活动描述给 100 字容纳简短规则说明；评论 140 字（对齐微博单条长度）防刷屏保排版；通知正文是唯一的长文位，给 2000 支持多段落；驳回原因 50 与列表展示宽度匹配。除协议明确生成的 `content_preview` 外，响应侧存量业务字段 schema 按契约风格不标请求长度；后端存量数据无需迁移（无上线用户）。

## 7. 资料修改频率限制（新增 `429` / `code=9`）

- 修改个人资料 `PUT /user/info`：昵称每自然月最多修改 **4 次**（按服务器时区，自然月初重置）。仅当请求携带 `nickname` 且与当前昵称不同时计 1 次，且成功修改才计数；提交相同昵称不计数、不报错。
- 修改头像 `PUT /user/avatar`：每自然月最多修改 **10 次**（同上计数口径，成功修改才计数）。
- 超限统一返回 `429`，新错误码 `code=9`（message 前缀「频率限制」），已登记进状态码表、错误码表和 OpenAPI `ErrorResponseBase.code` 枚举；两个 operation 的 `responses` 已声明 `429` 及示例。不新增剩余次数查询接口。
- 实现只需按（用户，自然月）计数；无上线用户，无历史数据回溯问题。
- 附带修正：`PUT /user/avatar` 此前从未声明 `400`，本轮补上（文件类型或大小不符，`code=3`），属声明缺口修正，行为不变。

行为含义：限制昵称频繁更换以保持社区内身份可辨识，限制头像反复上传以控制存储与审核成本。数值(4/10)后续调整属于放宽或收紧校验，按契约流程改文档即可。

## 8. 删除答题文字字段 `answer_text`（字段删除）

- 从以下 3 处 schema 及对应示例中整体删除 `answer_text`：提交答题 `POST /photos/{id}/attempts` 请求、图片答题列表 `GET /photos/{id}/attempts` 列表项、`UserAttemptItem`（用户在某图片下的答题列表与我的答题列表共用）。该字段因此不在 §6 的长度定稿表中。
- 答题的构成改为：猜测图片 `image_file` + 猜测坐标，判定与展示均不再有自由文本。

行为含义：管理端答题列表本就不返回 `answer_text`，审核判定只依据猜测图片与坐标，该字段对判定无贡献；但它会在客户端答题列表公开展示，且答题审核（`solved`/`unsolved`）并不是对文本的内容审核，等于一个未经审核的公开文本发布口。删除后表达类需求统一由评论承载（评论有独立审核流程）。属于删除字段的破坏性改动，两端未上线按可重写对待；后端可一并删除对应存储列，无历史数据迁移问题。

## 9. 活动结束后公开题目答案坐标（新增响应字段）

- 图片详情 `GET /photos/{id}`：新增**条件返回**字段 `longitude`、`latitude`、`coord_type`——仅当题目所属活动已结束（服务器时间 ≥ `end_time`）时返回，活动进行中或未开始时这三个字段不出现在响应中；坐标为投稿时提交的原始值与坐标系。字段不进 `required`，前端以字段是否存在判断答案是否已揭晓。
- 该 operation 的 `description` 原本已写明「活动结束后揭晓真实坐标」，但 schema 从未声明过这三个字段（文字与结构脱节），本轮补全使其可实现、可生成类型。
- 附带修正：我的投稿详情 `GET /photos/review/{id}` 原本返回 `longitude/latitude` 却缺 `coord_type`（没有坐标系的经纬度无法正确落图），本轮补上（必返）。用户答题记录 `UserAttemptItem` 同步补上必返 `coord_type`；管理端答题列表同时补上 `guess_coord_type` 与题目答案的 `coord_type`。
- 公开题目卡片（`PhotoCard` / `UserPhotoCard`）不新增题目答案坐标，答案只在详情接口揭晓；用户答题记录保留已有的猜测坐标并补齐 `coord_type`，管理端审核列表返回管理所需的题目答案坐标及两套坐标系。均为新增响应字段，非破坏性改动。

行为含义：活动进行期间坐标是谜底，必须由接口层面不下发（不能依赖调用方隐藏）；结束后详情接口可返回答案位置。活动一旦结束并可能公开坐标，不允许再通过更新活动把 `end_time` 延长到当前时间之后重新开放；若需提前结束可将 `end_time` 调到当前时间之前，但之后同样不可撤回。管理端题目池和答题审核列表一直返回管理所需的坐标及坐标系。

## 10. `ActivityBrief` 精简（字段删除）

- `ActivityBrief` 由原来的 `id`、`title`、`description` 收紧为仅 `id`、`title`；共影响 5 个 schema 使用点（图片详情、我的投稿详情、图片/投稿卡片、用户答题项、管理端题目池），Markdown 示例中对应的 7 处嵌套 `activity` 也同步删除 `description`。
- 这是响应字段删除的破坏性改动；两端尚未上线，按可重写处理。完整活动列表和活动详情自身仍保留活动 `description`，只精简嵌套的活动摘要。

## 11. 校验结果

`apifox-import.json` 与 `api.md` 当前均为 **72** 个 operation，已通过 `check_contract.py` 一致性校验（JSON 合法性、`operationId` 唯一性、`$ref` 可解析、两份文档接口清单双向一致）。

本轮另新增公共 schema `StandardErrorResponse`（继承 `ErrorResponseBase`、`resp` 固定为 `null` 的标准错误响应），供各接口本轮补齐的 `400`/`429` 等错误声明统一引用，无业务字段含义变化。
